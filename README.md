# Автоматический расчёт заказов поставщикам

Кейс HackAlem AI от ТОО «Электрокомплект» (ekt.kz): автоматизация формирования заказов поставщикам
для пополнения склада.

## Проблема и для кого

Менеджер отдела закупа считает потребность в пополнении склада вручную в Excel. Поэтому расчёт
делается редко. Разовые крупные продажи одному клиенту раздувают «регулярный» спрос, а месяцы, когда
товара не было на складе, наоборот, занижают его. В итоге по одним позициям копятся излишки, по другим
случается дефицит и упущенные продажи.

**Пользователь** — менеджер отдела закупа. **Сценарий:** запускает расчёт по поставщику или группе
товаров → получает список рекомендованных заказов с обоснованием по каждой позиции → проверяет,
при необходимости правит количество → утверждает → выгружает заказ в xlsx для 1С.
Поставщику ничего не отправляется автоматически.

Пример из реальных данных: розетка BRITE IP44 (код 1С `030200519_`). В апреле 2026 одна накладная
на 175 шт. при обычных 1–20 шт. в месяц, в мае 2026 товара не было на складе. Расчёт по «сырым»
продажам даёт заказ 16 шт. Сервис исключает разовую продажу, восстанавливает спрос за май и видит, что
текущего остатка (28 шт.) хватает до следующего цикла, поэтому заказ — 0.

## Что реализовано

Все пять обязательных требований кейса:

1. **Базовая потребность по каждому артикулу** с учётом истории продаж, текущих остатков, товаров в
   пути, группы товаров (сезонность и рост группы входят в прогноз), кратности поставщика, срока
   поставки из справочника поставщиков и прогноза по приросту (по истории или планового, задаётся
   менеджером). Изменение любого источника меняет результат — это видно на странице
   «Проверка расчёта» и проверяется тестами.
2. **Сезонность и устойчивый рост спроса.** Сезонный индекс по месяцам (по поставщику и по артикулу)
   и рост год к году.
3. **Оценка и компенсация упущенного спроса** в месяцы, когда товара не было на складе.
4. **Выявление и исключение разовых крупных заказов**, включая крупные продажи одному клиенту.
5. **Итоговый список заказов по поставщикам** (вкладки IEK / Systeme Electric) с обоснованием по
   каждой строке.

Опциональные требования, которые тоже сделаны: приоритизация по риску дефицита (срочность и «дней
хватит»), учёт минимальной партии / кратности поставщика, визуализация спроса по артикулу.

Дополнительно:

- правка количества, утверждение и отклонение позиций, экспорт утверждённого заказа в xlsx;
- страница «Проверка расчёта»: один артикул в восьми сценариях (разовая продажа, в пути, остаток,
  прирост, без учёта дефицита, без сезонности) — наглядная проверка требований 1–4;
- «Объяснить простыми словами»: языковая модель пересказывает уже посчитанное обоснование понятным
  текстом; без ключа API работает шаблон;
- по каждой позиции показывается, какой была бы рекомендация без очистки данных.

## Как работает решение

```
выгрузки 1С (xlsx) ──► loaders.py ──► единый формат: продажи SKU×месяц, остатки, накладные,
                                       в пути, кратность, сезонность
                                           │
                                           ▼
                                      engine.py ──► количество, срочность, обоснование по SKU
                                           │
                                           ▼
                        services.py ──► БД (CalculationRun, OrderLine)
                                           │
                                           ▼
          Django-страницы: расчёт → список по поставщикам → правка/утверждение → экспорт xlsx
                                           │
                                  llm.py (необязательно): объяснение простыми словами
```

## Методика расчёта

Расчёт детерминированный и полностью объяснимый. Для каждого артикула, у которого были продажи
за последние 12 месяцев:

1. **Спрос по месяцам** берётся из месячного отчёта продаж 1С за 24 полных месяца. Текущий неполный
   месяц в историю не входит.
2. **Исключение разовых крупных заказов и всплесков** (подробно ниже).
3. **Восстановление упущенного спроса.** Месяц считается месяцем дефицита, если остаток на начало
   месяца или на начало следующего месяца ≤ 0 (товар закончился в течение месяца). Спрос такого
   месяца заменяется на `max(факт, ожидаемый)`, где ожидаемый = средний спрос по месяцам без дефицита
   × сезонный индекс месяца. Спрос **не** восстанавливается, если товара нет 6+ месяцев подряд до
   текущей даты (похоже, позиция не закупается) или в названии стоит пометка «!!!» (см. допущения).
   Такие позиции отмечаются «проверить», а позиции с «!!!» автоматически к заказу не предлагаются —
   в обосновании указано, сколько нужно по расчёту, менеджер может вписать количество сам.
4. **Сезонность.** Индекс поставщика: продажи по месяцам (файл сезонности) делятся на центрированную
   скользящую среднюю 2×12, так рост или падение продаж не искажают сезонность. Индексы усредняются по
   одноимённым месяцам и нормируются к среднему 1. Тем же методом считается индекс **группы товаров**
   по суммарным продажам группы (если в ней ≥ 5 артикулов с продажами). Итоговый индекс: артикул 50%,
   группа 25%, поставщик 25%; если у артикула мало истории (< 100 ед. или < 12 месяцев с продажами) —
   группа и поставщик поровну.
5. **Рост.** Отношение последних 12 месяцев к предыдущим 12 — смесь артикула (ограничено 0,5–1,5),
   группы (0,7–1,4) и поставщика (0,8–1,25) в тех же долях, либо плановый прирост, заданный менеджером. Применяется от середины окна истории до середины
   горизонта прогноза.
6. **База** = среднее за 12 месяцев очищенного спроса без сезонной составляющей.
7. **Прогноз на горизонт** = база × сезонный индекс × рост, по дням. Горизонт = срок поставки + период
   между заказами (по умолчанию 30 дн.). Срок поставки берётся из справочника поставщиков в
   `constants.py`; если там не задан — выводится из заказов в пути; на форме расчёта его можно
   переопределить отдельно для каждого поставщика.
8. **Страховой запас** = z × σ × √(срок поставки / 30), z = 1,65 (~95%). σ считается устойчиво к
   выбросам: `max(1,4826 × MAD, √база)`.
9. **К заказу** = прогноз + страховой запас − текущий остаток − товар в пути, округление вверх до
   кратности поставщика. Отрицательное → 0.
10. **Срочность.** Сколько дней хватит остатка (плюс товара в пути, который придёт до новой поставки)
    с учётом сезона: меньше срока поставки — высокая, меньше горизонта — средняя, иначе низкая.

## Алгоритм исключения выбросов (разовых крупных заказов)

В выгрузке нет ID клиента, поэтому **одна расходная накладная считается одной сделкой с одним
клиентом**. Для каждого артикула по строкам накладных за 24 месяца:

- `med` — медиана количества в строке накладной, `MAD` — медиана абсолютных отклонений от `med`;
- строка считается разовым крупным заказом, если **одновременно**:
  - `qty > max(med + 5 × 1,4826 × MAD, 3 × med)` — аномально большая для этого артикула;
  - `qty > 1,5 ×` медиана ненулевых месячных продаж — одна накладная больше обычного месяца;
  - `qty ≥ 40%` продаж артикула в этом месяце — именно она сделала месяц аномальным;
- из спроса месяца вычитается превышение `qty − med`. Обычную часть заказа оставляем, потому что
  клиент купил бы типичное количество и без крупной сделки.

**Второй уровень — всплески в месячном отчёте без крупной накладной** (фильтр Хампеля). Нужен, потому
что построчные продажи и месячный отчёт 1С расходятся, и крупная продажа может быть видна только в
месячном отчёте. По ненулевым месяцам артикула после снятия сезонности (индекс поставщика):
месяц — всплеск, если он больше `max(медиана + 5 × 1,4826 × MAD, 4 × медиана)`. Такой месяц заменяется
типичным (медиана × сезонность). Пороги `MONTH_SPIKE_K`, `MONTH_SPIKE_RATIO` — в `constants.py`.

Медиана и MAD устойчивы к самим выбросам, в отличие от среднего и стандартного отклонения. Пороги
(`OUTLIER_MAD_K`, `OUTLIER_MONTH_SHARE`) настраиваются в `constants.py`. Исключённые накладные с
номерами и датами перечисляются в обосновании позиции и отмечаются на графике артикула.

## Технологии

- Python 3.10+, Django 5 (веб-интерфейс, SQLite для хранения расчётов и правок);
- pandas, numpy — расчёт;
- openpyxl — чтение выгрузок 1С и экспорт заказа в xlsx;
- OpenAI API или NVIDIA API (OpenAI-совместимый) — необязательно, только для текста «Объяснить
  простыми словами». Вызов через стандартную библиотеку `urllib`, без SDK;
- графики — SVG, генерируются на сервере, без JS-библиотек;
- шрифт Golos Text с Google Fonts. Без интернета подставляется системный шрифт.

## Архитектура проекта

```
constants.py                 все настройки и параметры расчёта (переменные окружения не используются)

supply/                      настройки Django
procurement/
  loaders.py     чтение и очистка шести выгрузок 1С на поставщика, кэш в data/cache/
  engine.py      методика расчёта (см. выше), класс Params — все параметры
  services.py    запуск расчёта и сохранение в БД
  llm.py         объяснение простыми словами: AI или шаблон
  charts.py      SVG-график спроса
  models.py      CalculationRun (запуск), OrderLine (строка заказа: рекомендация, правка, статус)
  views.py       страницы: расчёт, результат, экспорт, проверка, данные, артикулы
  tests.py       тесты на все 5 обязательных требований (синтетические данные)
data/demo/iek/, data/demo/se/   выгрузки партнёра
```

## Установка и запуск

Нужен Python 3.10 или новее.

```bash
git clone <репозиторий>
cd <папка репозитория>

python -m venv venv
# Linux / macOS:
source venv/bin/activate
# Windows:
venv\Scripts\activate

pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Откройте http://127.0.0.1:8000/.

Первое открытие страниц с данными занимает 20–30 секунд: разбираются xlsx-файлы (~250 тыс. строк).
Дальше данные берутся из кэша `data/cache/`.

## Зависимости

`requirements.txt`: Django ≥ 5.0, < 6.0; pandas ≥ 2.0; numpy ≥ 1.24; openpyxl ≥ 3.1.
Больше ничего не требуется, база данных — SQLite (создаётся командой `migrate`).

## Параметры окружения

Переменные окружения не используются. Все настройки — в `constants.py`:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `DEFAULT_LEAD_TIME_DAYS` | 40 | срок поставки, если нет в справочнике и нельзя вывести из данных |
| `REVIEW_PERIOD_DAYS` | 30 | период между заказами |
| `SERVICE_LEVEL_Z` | 1,65 | уровень сервиса для страхового запаса (~95%) |
| `HISTORY_MONTHS` | 12 | окно для базового спроса |
| `OUTLIER_MAD_K` | 5 | порог разового заказа, в MAD |
| `OUTLIER_MONTH_SHARE` | 0,4 | минимальная доля разового заказа в продажах месяца |
| `MONTH_SPIKE_K`, `MONTH_SPIKE_RATIO` | 5; 4 | порог всплеска месяца без накладной |
| `LONG_STOCKOUT_MONTHS` | 6 | после стольких месяцев без товара спрос не восстанавливается |
| `DISCONTINUED_MARK` | «!!!» | пометка в названии 1С, при которой позиция не предлагается автоматически |
| `SUPPLIERS[...]["lead_time_days"]` | IEK — авто, SE — 40 | справочник сроков поставки |
| `LLM_PROVIDER` | openai | `openai` или `nvidia` |
| `OPENAI_API_KEY`, `NVIDIA_API_KEY` | пусто | ключи AI, **необязательно** |

**Ключи API не нужны для проверки.** Без них всё работает, объяснение формирует шаблон.
Чтобы включить AI, скопируйте `local_constants.example.py` в `local_constants.py` и впишите ключ
(и при необходимости `OPENAI_MODEL` — любую доступную вашему ключу chat-модель). Файл
`local_constants.py` в `.gitignore`.

## Как проверить решение

**Автоматически** — тесты на каждое обязательное требование:

```bash
python manage.py test procurement
```

| Тест | Требование |
|---|---|
| `MustHave1AllSourcesUsed` | в пути, остаток, плановый прирост, срок поставки, кратность, фильтр группы меняют результат |
| `MustHave1CategoryMatters` | смена группы товара меняет сезонность и рекомендацию |
| `MustHave2Seasonality` | для сезонного товара прогноз выше среднего в сезон и ниже вне сезона |
| `MustHave3Stockout` | при дефиците потребность выше, чем по «сырым» продажам |
| `MustHave4OneOffOrders` | разовый заказ на 2000 шт. (в накладных или только в месячном отчёте) почти не меняет рекомендацию; без очистки — рост в разы |
| `StockoutEdgeCases` | долгое отсутствие и пометка «!!!» — спрос не выдумывается, позиция помечается «проверить» |
| `MustHave5GroupedWithReasons` | у каждой строки есть обоснование, строки привязаны к поставщику |

**Вручную, основной сценарий (≈ 3 минуты):**

1. Главная → «Рассчитать заказы» (все поставщики, настройки по умолчанию). Расчёт идёт ~10–30 с.
2. Откроется список по поставщикам: срочные позиции сверху. У любой строки раскройте
   «Почему столько», затем нажмите «Объяснить простыми словами». Фильтр «Требуют проверки» покажет
   позиции с пометкой «!!!» и долгим отсутствием товара.
3. Поменяйте количество в колонке «К заказу» у пары строк, отметьте их, нажмите «Утвердить
   отмеченные», затем «Выгрузить утверждённое» — скачается xlsx.
4. Меню «Проверка расчёта». По умолчанию артикул IEK `030201020_` (розетка BRITE бежевая).
   Ожидаемо: базовый расчёт ≈ 74; с разовой продажей ≈ 700 шт. — почти столько же (≈ 79); та же
   продажа без очистки — ≈ 259; та же продажа только в месячном отчёте, без накладной — ≈ 70;
   с товаром в пути и большим остатком — меньше; смена группы товаров — другое значение; без учёта
   дефицита — меньше; без сезонности — меньше (горизонт попадает на сезонный пик).
   Можно ввести любой код и свои значения.
5. Меню «Артикулы» → `030200519` → график: оранжевый столбец — апрельская разовая продажа,
   розовая зона — май без товара, линия — спрос, который пошёл в расчёт.

Точные цифры зависят от даты данных (22.09.2026) и могут немного отличаться после изменения параметров.

## Данные и интеграции

Выгрузки партнёра лежат в репозитории, `data/demo/<поставщик>/`; имена файлов переведены в латиницу:

| Файл | Исходное название | Содержимое |
|---|---|---|
| `sales_transactions.xlsx` | Динамика продаж | строки расходных накладных: дата, номер, код 1С, количество, склад |
| `sales_monthly.xlsx` | Ежемесячные продажи в кол-ве | продажи SKU × месяц, 2024–2026 |
| `stock_monthly.xlsx` | Ежемесячные остатки | остаток на начало месяца, SKU × месяц |
| `in_transit.xlsx` | Путь / Товар в пути | IEK — заказы с датами; SE — отчёт закупщика с «в пути», категорией, свободным остатком |
| `moq.xlsx` | MOQ | минимальная партия / кратность |
| `seasonality.xlsx` | Сезонность | продажи в деньгах по месяцам и годам |

**Допущения, принятые по данным:**

- Нет ID клиента → одна накладная = одна сделка одного клиента.
- Построчные продажи расходятся с месячным отчётом 1С примерно на 40% (у IEK меньше, у SE больше).
  Поэтому спрос берётся из месячного отчёта, а накладные — только для поиска разовых заказов.
  Расхождение показывается на странице «Данные».
- Нет явных периодов stockout → определяются по месячным остаткам (точность — месяц).
- Пометка «!!!» в названии (276 арт.) трактуется как «выводится из ассортимента / не заказывать»:
  продажи за год есть только у ~35–60% таких позиций против 82–92% у остальных. Это допущение —
  позиции не скрываются, а помечаются «проверить», решение остаётся за менеджером.
- Срок поставки IEK — 24 дн.: медиана по заказам в пути, взвешенная по количеству. У SE дат заказа
  нет → 40 дн. из справочника поставщиков в `constants.py`. Срок можно задать вручную при запуске.
- Текущий остаток: SE — свободный остаток из отчёта закупщика; IEK — остаток на 1 сентября минус
  продажи сентября по месячному отчёту 1С (из того же отчёта, что и остатки).
- Групп товаров в явном виде нет → группа = первые 4 цифры Кода 1С (например, у IEK 0302 —
  розетки, выключатели и рамки, в основном серия BRITE). У SE дополнительно показывается «Категория 2026» из отчёта.

**Приватность.** В данных нет персональных данных клиентов. В AI-объяснение уходят только агрегаты
по артикулу: спрос, остаток, в пути, номера исключённых накладных.

**Совместимость с учётной системой.** Экспорт — xlsx, одна строка на артикул, ключ — Код 1С,
на каждого поставщика отдельный лист.

## Ограничения

- Данные загружаются из файлов в `data/demo/`. Чтобы пересчитать на новой выгрузке, замените файлы
  (с теми же именами) и нажмите «Перечитать файлы» на странице «Данные». Загрузки файлов через
  интерфейс нет.
- Один склад (Алматы); расчёт по складам не разделяется.
- Дефицит определяется по месячным остаткам. Если товар кончился и пришёл внутри месяца, это может
  быть не замечено.
- Кабель закупается бухтами, а продаётся метрами. Кратность берётся из файла MOQ как есть,
  перевод единиц не делается.
- Для новых товаров с короткой историей прогноз менее точен (используется сезонность поставщика).
- Автоматической отправки заказа поставщику нет — по требованию кейса, только утверждение и выгрузка.
- Развёрнутой версии нет, запуск локальный.
